=== [TOPIC: Advanced RAG Architecture & Unique Production Features] ===

WHAT IT IS:
  Retrieval-Augmented Generation (RAG) lets an AI answer questions using your specific documents instead of its static pre-trained memory. While "naive RAG" just slices text and does a basic vector search, a "production-grade RAG API" adds precision layers like hybrid keyword search, re-ranking, smart chunking, and non-blocking async background processing.

HOW IT WORKS (step by step):
  1. Ingestion & Hierarchical Chunking: Large documents are broken into small child chunks for pinpoint search, linked to larger parent chunks for full context.
  2. Multi-Stage Retrieval (Hybrid Search): The system searches using BOTH vector similarity (meanings) and BM25 search (exact keywords), then merges rankings with Reciprocal Rank Fusion (RRF).
  3. Re-Ranking: A Cross-Encoder model re-evaluates the top candidates to pick only the most accurate context.
  4. Generation & Streaming: The LLM processes the re-ranked parent context and streams back token-by-token responses using Server-Sent Events (SSE).
  5. Async Ingestion Queue: Heavy PDF parsing happens in background threads so the API stays lightning fast and responsive.

THE CODE DOES THIS:
  - We researched modern patterns to expand standard FastAPI + ChromaDB/Qdrant setups into robust, production-grade backends.
  - Future modules will include `ingestion.py` (parent-child chunking & async queues), `retrieval.py` (hybrid BM25 + dense search + re-ranking), and `main.py` (streaming SSE endpoints).

ANALOGY:
  Imagine a detective searching a library. Naive RAG is like using only a subject index. Advanced RAG is using both the subject index AND exact keyword search (Hybrid), sorting through the top matching book chapters with a fine-tooth comb (Re-ranking), reading the full page around a key sentence (Parent-Child chunking), and walkie-talkieing findings back to base line-by-line in real time (Streaming).

COMMON MISTAKES:
  - Relying solely on vector search: Misses exact term matches (like code snippets, product IDs, or uncommon names).
  - Fixed-size chunking: Slices sentences in half, causing context loss.

=== [TOPIC: How Standard RAG Q&A Endpoints & Data Flow Work] ===

WHAT IT IS:
  A baseline RAG Q&A API provides an automated pipeline to ingest documents (PDF/TXT), turn text into mathematical vector embeddings, store them in a persistent vector database (ChromaDB), search relevant document sections when a user asks a question, and synthesize grounded answers with source citations.

HOW IT WORKS (step by step):
  1. Document Upload (`POST /upload`):
     - PDF/TXT file is read into bytes.
     - PyMuPDF extracts raw text page by page (tracking page numbers).
     - RecursiveCharacterTextSplitter breaks text into 500-character chunks with 50-character overlap.
     - Each chunk text is passed to SentenceTransformers (`all-MiniLM-L6-v2`) to generate a 384-dimensional vector embedding.
     - Chunk text + vector + metadata (`doc_id`, `filename`, `page_number`) are saved to ChromaDB on Drive E.
  2. Question Answering (`POST /query`):
     - The user's question is converted into a vector embedding using the exact same embedding model.
     - ChromaDB performs cosine similarity search to retrieve top-K matching text chunks.
     - Matching chunks are formatted into a context block with page citations.
     - Prompt synthesis combines the context + question to output a grounded answer without hallucinations.
  3. Document Management (`GET /documents` & `DELETE /documents/{doc_id}`):
     - `GET /documents` aggregates ChromaDB metadata to list all indexed document IDs and chunk counts.
     - `DELETE /documents/{doc_id}` purges all vector embeddings associated with that `doc_id`.

THE CODE DOES THIS:
  - `app/config.py`: Stores configuration & isolates all storage paths on Drive E.
  - `app/models.py`: Defines request/response data shapes using Pydantic V2.
  - `app/vectorstore.py`: Wraps ChromaDB persistent vector database & embeddings.
  - `app/ingestion.py`: Extracts PDF text page by page and chunks text.
  - `app/retrieval.py`: Searches vector DB, constructs context, and generates answers.
  - `app/main.py`: Exposes FastAPI REST API endpoints.

ANALOGY:
  Imagine a smart librarian. When you hand them a book (`POST /upload`), they chop the chapters into labeled flashcards, generate index numbers, and put them in a filing cabinet (ChromaDB). When you ask a question (`POST /query`), they look up matching flashcards, read them, and write down a direct answer for you with exact page references!

COMMON MISTAKES:
  - Not tracking page numbers during ingestion: Leaves the user guessing where in the document an answer came from.
  - Mismatched embedding models: Using model A to embed documents and model B to embed questions produces garbage search results.

=== [TOPIC: RegEx Pattern Collisions & Field Disambiguation in Form Extraction] ===

WHAT IT IS:
  When extracting specific fields (like an applicant's name) from a structured document using regular expressions, loose keyword matching (e.g. matching `Name`) can accidentally match OTHER fields that contain the word "Name" (such as `Institute Name: Example: DU` or `Father's Name`). This is called a "Pattern Collision".

HOW IT WORKS (step by step):
  1. Root Cause Identification:
     - The loose regex `(?:Full Name|Name)[^\n:]*[:\*\s]+([A-Za-z]+)` matched `Institute Name \n Example: DU`.
     - It returned `Example` as the applicant name!
  2. Disambiguation Fix (`app/retrieval.py`):
     - Require exact target field prefixes (`Full Name`, `Nick Name`, `বাংলায় সম্পূর্ণ নাম`).
     - Filter out placeholder/label words like `Example`, `Institute`, `Department`, `Father`, `Mother`, `College`.

THE CODE DOES THIS:
  - `app/retrieval.py`: `re.findall(r'(?:Full Name|বাংলায় সম্পূূর্ণ নাম|Nick Name)...')` extracts exact target values.

ANALOGY:
  Imagine looking for a person named "King" in a dictionary. If you search for any word containing "king", you will accidentally get "Parking", "Thinking", and "Walking"! You must search specifically for the exact full name "King" to avoid catching unrelated words.

COMMON MISTAKES:
  - Using overly broad regex patterns (like matching `Name`) on form documents with multiple name fields (`Institute Name`, `Father Name`, `Mother Name`).

=== [TOPIC: Why RAG Gives Bad Answers & How To Fix It] ===

WHAT IT IS:
  A RAG system can give poor answers even when the code looks correct. This is because answer quality depends on 4 separate layers working together: (1) text extraction quality, (2) embedding model language match, (3) retrieval chunk coverage, and (4) answer synthesis strategy.

HOW IT WORKS (step by step — diagnosing poor answers):
  1. Layer 1 — Text Extraction: If the PDF has fragmented glyphs (e.g. 'N a m e' or 'খা তা'), the indexed text is broken and vector search finds nothing useful.
  2. Layer 2 — Embedding Model Mismatch: If your document is in Bengali but the embedding model was trained only on English (`all-MiniLM-L6-v2`), similarity scores are meaningless. Use a multilingual model.
  3. Layer 3 — Insufficient Retrieval Coverage: If `top_k=3` and `chunk_size=500`, only ~1500 characters reach the synthesizer. For long multi-page documents, the answer is likely on a page that wasn't retrieved.
  4. Layer 4 — Synthesis Strategy: Without an LLM API key, only hardcoded regex runs. If the question doesn't match any regex pattern, the system dumps raw text instead of giving a real answer.

THE CODE DOES THIS:
  - `app/config.py`: Controls `CHUNK_SIZE`, `CHUNK_OVERLAP`, `DEFAULT_TOP_K`, and `EMBEDDING_MODEL_NAME`.
  - `app/ingestion.py`: `clean_and_normalize_text()` fixes glyph fragmentation before chunking.
  - `app/retrieval.py`: `synthesize_answer()` tries Gemini → OpenAI → local extractor in order.

ANALOGY:
  Imagine a doctor diagnosing a patient. If the X-ray machine is broken (Layer 1), the lab test uses wrong reagents (Layer 2), only 3 test results are checked out of 100 (Layer 3), and the doctor has no medical knowledge (Layer 4) — the diagnosis will always be wrong, even though the hospital building looks fine!

COMMON MISTAKES:
  - Assuming the code is wrong when actually the embedding model doesn't support the document's language.
  - Using `top_k=3` for large documents: always use 6–10 for multi-page PDFs.

=== [TOPIC: Choosing the Right Embedding Model for Your Language] ===

WHAT IT IS:
  An embedding model converts text into a numerical vector. The quality of vector similarity search depends entirely on whether the model "understands" the language of your documents. Using an English-only model for Bengali documents produces random-quality results.

HOW IT WORKS (step by step):
  1. English-Only Model (`all-MiniLM-L6-v2`): 384-dimensional vectors. Trained on English web/book text only. Completely unreliable for Bengali, Arabic, Chinese, etc.
  2. Multilingual Model (`paraphrase-multilingual-MiniLM-L12-v2`): 384-dimensional vectors. Trained on 50+ languages including Bengali (bn), Arabic (ar), Hindi (hi), etc. Drop-in replacement — same vector size, same API.
  3. Model Change = Collection Reset: When you change the embedding model, ALL previously indexed vectors become meaningless (wrong dimensions or wrong semantic space). You MUST delete the old ChromaDB collection and re-index all documents.

THE CODE DOES THIS:
  - `app/config.py`: `EMBEDDING_MODEL_NAME` and `COLLECTION_NAME` control which model and which DB collection are used.
  - Changing `COLLECTION_NAME` to a new name (e.g., `rag_documents_v2`) forces ChromaDB to create a fresh empty collection automatically.

ANALOGY:
  Imagine two librarians: one only speaks English, the other speaks 50 languages. If you hand the English-only librarian a Bengali book and ask "find me books about education," she will pick random books because she cannot read Bengali. The multilingual librarian finds the right books immediately.

COMMON MISTAKES:
  - Not changing `COLLECTION_NAME` after switching models: old and new vectors get mixed in the same collection, producing garbage search results.
  - Forgetting to re-upload documents after a model change.

=== [TOPIC: Environment Variables & .env Files for API Keys] ===

WHAT IT IS:
  Sensitive credentials like API keys must NEVER be hardcoded in Python source files. Instead, they are stored in a `.env` file (a simple key=value text file) which is loaded automatically by `pydantic-settings` via `env_file = ".env"` in `app/config.py`. The `.env` file should NEVER be committed to Git.

HOW IT WORKS (step by step):
  1. Create `.env` file: Place it in the project root (`e:/job_project/restapi/.env`).
  2. Write key-value pairs: `GEMINI_API_KEY=AIza...your_key_here`
  3. `pydantic-settings` loads it: Any `class Settings(BaseSettings)` with `env_file = ".env"` automatically reads all keys from the `.env` file into Python.
  4. `os.environ.get("GEMINI_API_KEY")` also reads it: Once loaded by Settings, the values are accessible anywhere in the app.
  5. Priority Order: `app/retrieval.py` checks `GEMINI_API_KEY` first → then `OPENAI_API_KEY` → then runs offline fallback.

THE CODE DOES THIS:
  - `app/config.py`: `class Config: env_file = ".env"` tells pydantic-settings to auto-load the file.
  - `app/retrieval.py`: `os.environ.get("GEMINI_API_KEY")` reads the key to decide which synthesizer to use.
  - `.env` file: Lives at `e:/job_project/restapi/.env`, add your key there.

ANALOGY:
  A `.env` file is like a locked personal safe in your office (Drive E). Your Python code is the employee who knows the safe combination (`os.environ.get`). The API key is the secret document inside — never left lying on the desk (never hardcoded in source files).

COMMON MISTAKES:
  - Hardcoding API keys directly in Python: Anyone who reads your code gets your key and gets billed.
  - Committing `.env` to Git: Add `.env` to `.gitignore` immediately.
  - Forgetting to restart the server after editing `.env`: The new key is only loaded at server startup.
